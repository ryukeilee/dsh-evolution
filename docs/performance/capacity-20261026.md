基线 `f469b8e`（`0.2.0-rc.18`）。本轮**保留三处改动**，其余候选全部撤回，撤回理由带复现，

## 1. 口径与环境

- Node `v22.23.4`，darwin/arm64，每个子进程 `--max-old-space-size=4096`；父进程驱动器自身也为 4096 MiB。
- 基线是 `/tmp/dsh-base`（`git worktree add` 于 `f469b8e`，`node_modules` 符号链接到候选工作树）；
  候选是本工作树。两侧用**同一份夹具字节**：先由候选树生成一次，再在每次采样前整目录复制到
  `mkdtemp` 的隔离 home（`caphome-*`），因此每次采样都是干净目录、单独进程。
- 夹具真实形状：`<home>/storages/evolution/` 是数据根，`<home>/storages/evolution_domain.json`
  是官方 JSON backend 的单元文件，`execution-events.jsonl` 是 `signEventBridgeEnvelope` 签出的真实
  信封（同一 `event-bridge.key`）。夹具生成后跑过一次真实 `port.flush()`，所以**存在有效 checkpoint**，
  这正是稳态启动的形状。
- 三个规模：244 条 / 200,014 B；12,254 条 / 10,135,542 B；61,269 条 / 50,853,479 B。
- A/B 交替：3 轮，每轮每 (规模 × workload) 两侧各一次，轮次间交换先后顺序。表中为 3 个样本的
  中位数；`wins` 是候选在多少个配对样本里更快/更省。
- 等价性：每个样本都记录了 `seen` 大小、`sequence`、日志 SHA-256、以及启动前后的领域文档
  SHA-256。全部样本两侧 `seen`/`sequence`/日志摘要完全相同，且两侧启动都没有改动领域文档字节。

## 2. 启动（端口 open + `EvolutionEventBridge` 构造）

| 规模 | 记录 | 日志字节 | 基线扫描 ms | 候选扫描 ms | 基线峰值 RSS | 候选峰值 RSS | RSS 变化 | 时间 wins / RSS wins |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 小 | 244 | 200,014 | 2.4 | 2.9 | 62.7 MB | 63.5 MB | +1.3% | 0/3 / 0/3 |
| 万级 | 12,254 | 10,135,542 | 96.0 | 94.3 | 154.1 MB | 128.1 MB | **−16.9%** | 3/3 / 3/3 |
| 更大 | 61,269 | 50,853,479 | 476.5 | 475.8 | 369.0 MB | 258.0 MB | **−30.1%** | 2/3 / 3/3 |

边界必须一起读：

- 峰值 RSS 是**整进程生命周期的高水位**（`process.resourceUsage().maxRSS`）。它包含模块加载、
  官方 backend 解析领域文档，以及同进程内的端口 open；差值是“整次启动”的差值，
  不是扫描单独分配了多少。本轮没有单独测量“只做构造”的净分配。
- 小规模上候选慢 0.5 ms（3 个样本全部如此，但绝对值是 0.5 ms，峰值 RSS 高 0.8 MB）。
  该夹具只有 200,014 B，全程只读一块，不涉及跨块拼接；成本来自多出的一次读取调用与
  逐行解码路径。在 10k/50k 上被省下的整文件字符串与行数组抵消。
- 收益维度是**峰值内存**，不是墙钟。墙钟在 10k/50k 上基本不变（−1.8% / −0.1%）。
- 审查后又测了一轮（2 轮 × 2 侧，同一夹具、同一脚本）确认把跨块 carry 改成一次性拼接后
  结论不变：50,000 规模 474.3 → 460.8 ms，峰值 RSS 403.1 → 255.5 MB（2/2 两侧均胜）。

## 3. 稳态 flush 与诊断

**稳态 `flush()`**（有效 checkpoint、无新事件，5 次的中位数）：

| 规模 | 基线 ms | 候选 ms |
| ---: | ---: | ---: |
| 小 | 0.27 | 0.27 |
| 万级 | 8.07 | 8.08 |
| 更大 | 42.40 | 41.98 |

本轮没有改 flush 路径，数值如上只为证明没有回归。两侧 flush 子进程的峰值 RSS 差异
（50k：406.8 MB → 258.6 MB）来自该进程里同时构造了 bridge，归因到 §2 的启动扫描，而不是 flush。

**诊断（完整隔离 home，27 个 check）**：

| 规模 | 基线 ms | 候选 ms | 基线峰值 RSS | 候选峰值 RSS |
| ---: | ---: | ---: | ---: | ---: |
| 小 | 11.9 | 11.9 | 59.3 MB | 59.2 MB |
| 万级 | 42.1 | 42.0 | 103.3 MB | 103.5 MB |
| 更大 | 144.0 | 144.6 | 291.0 MB | 291.5 MB |

在完整 home 上，大历史诊断的峰值两侧都是 291.0 / 291.5 MB、耗时基本不变。把夹具收窄到
只有日志（没有领域文档、没有冷档案）：

| 基线 ms | 候选 ms | 基线峰值 RSS | 候选峰值 RSS | `lines` / `verifiedEvents` / level |
| ---: | ---: | ---: | ---: | --- |
| 500.6（499.8/500.6/508.9） | 497.4（496.9/497.4/500.5） | 316.8（317.2/316.8/316.8） | 99.7（99.3/99.7/100.3） | 61,269 / 61,269 / `ok`，两侧完全相同 |

两个夹具的成分不同（一个有 61,269 个 marker 的领域文档与冷档案，一个只有日志），所以两张表
不能相减分解出“每个 check 占多少”；能说的是：完整 home 的整体峰值本轮不变，而被改写的
那一个 check 在它自己的夹具上峰值下降 68.5%。

`state.event-bridge` 现在额外报告 `absorbedRecords` / `unabsorbedRecords` /
`oldestRecordAt` / `newestRecordAt`。这四个字段只在 `state.domain` 已经完整校验时出现；
拿不到权威 marker 集合时它们**整体缺席**，而不是填一个更小的数。它不是新的 check id，
不改变 level、summary、remediation 或 repair。

## 4. 撤回的候选与反例

### 4.1 自动接通 `maintenance()`（撤回，两个已复现阻塞）

现状：`EvolutionMemory.maintenance()`（48 MiB 触发 + 10 分钟冷却）、`compact()`、
`archiveDiagnostics()` 在 `lib/` 里**没有生产调用者**，`EvolutionDiagnostics` 的 27 个 check 也不读它们。
构造器注释承诺"periodic schedulers ask maintenance()"，但插件没有 scheduler，端口也没有暴露该方法。

实现前做了两轮独立审查，各自复现了阻塞：

1. **旧段复活。** `changedArchiveFiles()` 只报告新增/修改，不表达能力"删除"；`installArchiveFiles()`
   只能原子替换。三段冷档案被压缩成一段后，安装只替换新的 active 段与新索引，旧的三段仍在
   live 目录里。重启时 `#archiveFiles()` 按实际目录枚举（不以索引为白名单），于是旧记录**复活**，
   与新聚合同时可读，而 `coldArchives` 计数却是 0。`verifyConsistency()` 抓不到。
2. **坏字节被"成功 GC"洗掉。** `#readArchiveSync()` 遇到不可解析行只登记 fault 并跳过，
   `#retentionPlan()`/`#rewriteArchives()` 不据此拒绝；于是一次成功提交会让源坏行与原故障一起消失。
   这直接违反 AGENTS.md §4 第 2 条"不得猜测、静默合并或删除现场"。
3. 次要但同样阻断：在同一个前台事务里吞掉 compact 失败后继续提交，无法证明隔离成功
   （`assertLiveTreeUnchanged` 只证明 live 未变，不证明 stage 完整）。

实测收益也支持"不值得为它背书"：20,000 个 experiment 的合成冷层 14,472,150 B → 13,210,120 B
（**−8.7%**，retired 2,858 行，compact 563 ms）。要拿到这 8.7% 需要一个删除语义 + 完整性门禁，
两者都是新的持久化协议，不属于本轮范围。**结论：保持 `maintenance()` 不被自动调用**，
`archiveDiagnostics()` 也仍未接线。

### 4.2 回收事件日志 / applied 标记（撤回，未实现）

`applied` 是重放去重权威：删掉一个老 marker、但日志行仍在，下一次重放会把该事件**再执行一遍**
（`replay-batch-commit.test.js` 已用 4,097 窗口的 canary 反例固化）。删掉日志行、保留 marker，
则失去 `readEventBridgeEvidence()` 所说的"老 promotion 唯一幸存的证据来源"。
两者都做则需要在 marker 裁剪、日志换 inode、replay floor 三者之间建立原子协议，
而当前没有这样的协议；`append.lock` 只串行字节，不能让另一个存活实例的 `seen`/`sequence` 失效。
按 AGENTS.md §4 第 2、11、14 条与"无法证明安全时只提供诊断"的要求，本轮不动日志与标记，
只把它们变成可观测的（§3）并记录边界（§6）。

### 4.3 其他被否决的方向（本轮未实现）

- **`EvolutionEventBridge.seen` 加容量上限。** 同一 eventId 重新签名会产生不同 MAC，replay 会
  报 `E_DOMAIN_EVENT_ID_CONFLICT` 并永久阻塞，不能按年龄丢 ID。
- **`patterns` / `candidates` / `suppressedPatterns` 加容量上限。** 三者都是进程内、按
  patternKey 一项；逐出会重置发生计数（延迟候选触发）、让 `inspect` 的 `evolutionCandidates`
  少项、或让已抑制的 low-risk 模式再次跑隔离 Trial。这是观察者对外可观察行为的变化，
  不是纯缓存，AGENTS.md §4 第 6 条不允许静默改默认行为。
- **跳过启动 `syncTree()` 的全树 fsync。** 当前事务已经 fsync 变更的 stage 文件与目录、
  安装后 fsync 目标目录；但没有任何持久 provenance 位能证明 live 树里每个文件都由当前协议写入，
  旧版本/显式 seed/外部放置的文件不在其内。没有证明就不删。
- **降低首次吸收时每次 save 的整份 payload 校验。** 见 §6 末段的实测归因；它是超线性
  首次启动的主要成本，但改动会移动 `transaction-save-validation` 与 `inlineSerialization`
  钉住的边界，本轮不动。


以及每个样本的 `seen`/`sequence`/日志摘要/领域文档不变性。

## 6. 容量边界（本轮交付后的真实承诺）

| 状态 | 是否有界 | 依据 |
| --- | --- | --- |
| 热池（18 个集合） | 是，`hotEntries`/`hotCycles`/`maxEntries` | 每次 `#save()` 都跑 housekeeping；归档失败时故意允许超限以不丢数据 |
| 冷档案字节 | **否** | `maintenance()` 未接线（§4.1）；只有轮转（每段 `archiveMaxBytes`），没有总量回收 |
| 冷档案读取缓存 | **否**（随冷层字节线性，约 0.7 MiB heap / MiB） | 构造器注释声称由 `compactionTriggerBytes` 约束，但该约束在本轮之后**仍不成立**；README 已知限制 13 保留原描述 |
| `execution-events.jsonl` | **否** | 每个执行事件一行；是审计与老 promotion 的最后证据（§4.2） |
| 领域 `applied` 标记 | **否**，上限 9 × experiment 数 | 去重权威，不可裁剪（§4.2） |
| 编排器 `patterns`/`candidates`/`suppressedPatterns` | 进程内按 patternKey 增长 | 有意的行为契约，不是缓存（§4.3） |
| 启动扫描的内存 | **是**（本轮） | 分块读，峰值与日志字节脱钩；`seen` 仍需 O(唯一事件数) |
| 诊断的内存 | **是**（本轮，日志部分） | 分块读；`byEventId` 仍需 O(唯一事件数) 用于冲突判定 |

**首次启动（无 checkpoint）的历史吸收成本是超线性的，本轮未改。** 同一台机器上实测：
3,000 条 3.57 s、6,000 条 10.25 s、12,000 条 24.84 s、73,525 条 298.05 s；同棵树在有效
checkpoint 下重启是 31 ms（12,000 条）。JS 侧归因：`JSON.stringify` 占该次 open 的 50%–60%，
每条被吸收记录触发约 95 次 `JSON.stringify` 调用（该计数直接测得，含每条记录的验签规范化；
其中全聚合的那部分来自事务内每次 `#save()` 的入口校验，这一项按代码路径归因，未单独计数）。
降低它需要改动"每次 save 都验证整份 payload"的既有边界（`transaction-save-validation`、
`inlineSerialization` 合同），因此不在本轮做。实际影响边界：正常重启不会走到这条路径，
只有 checkpoint 丢失/失效或长时间停机后的大积压会。
